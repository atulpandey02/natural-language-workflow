# ADR-025 — Release-manifest provenance (trusted release authority)

Status: accepted (M12A-Prep correction) · Date: 2026-09-22 · Relates to: ADR-018 (immutable images), ADR-024 (signed database context)

## Context

The M12A rollout takes its release identity (git SHA, backend/web image
digests, expected/target migration, instance identity, key ids) from an
external JSON manifest generated by CI (`nlw.ops.release_manifest`). Before this
decision the rollout accepted any file that was **structurally** valid. A
regression test (`tests/unit/test_release_provenance.py::test_hand_written_ci_manifest_…`)
reproduces the weakness: a JSON written by hand with `kind: release`,
`deployable: true`, `generated_by: ci`, a real full SHA, plausible immutable
digests and the expected environment/instance/migration values passes schema
validation — and, if it names real current images, passes image
capability/identity verification too. Nothing proved the bytes came from the
trusted workflow. The earlier claim "a locally edited JSON cannot become
authority" was not supported.

## Decision

Three independent checks are all mandatory for a staging/production rollout:

| check | module / phase | prevents |
|---|---|---|
| Schema validity | `nlw.ops.release_manifest` | malformed, non-deployable, secret-bearing, inconsistent manifests |
| Image capability / identity | rollout `verify-release` (`gates.check_image_info`, revision labels, required commands) | incompatible or mismatched images (e.g. the old `1eebf2e` image) |
| **Provenance / authenticity** | `nlw.ops.release_provenance` | any manifest not produced by the trusted workflow for the exact merged-main commit |

Provenance uses **GitHub artifact attestations** (`actions/attest-build-provenance`,
Sigstore keyless signing with the workflow's OIDC identity, SLSA v1 provenance).
The Delivery workflow (`.github/workflows/staging.yml`, `push` to `main` only)
attests three subjects in the same run after both images are final: the
release-manifest bytes (whose content includes both image digests and the
release SHA), the backend image digest and the web image digest (image
attestations pushed to GHCR). No custom cryptography; no long-lived signing key
in the repository.

The verifier (`python -m nlw.ops.release_provenance verify`) runs
`gh attestation verify` (signature, transparency log, certificate chain) with
exact constraints and then **re-evaluates the certificate extensions and the
SLSA predicate in code** (`evaluate_attestation`) plus the run metadata
(`evaluate_run`):

* subject sha256 == the manifest bytes / the image digest;
* OIDC issuer `https://token.actions.githubusercontent.com`;
* source repository `atulpandey02/natural-language-workflow`;
* signer workflow `.github/workflows/staging.yml@refs/heads/main`;
* source ref `refs/heads/main`; event `push`; runner `github-hosted`;
* source commit == the manifest's `release_sha`;
* the attested run == the run named in the manifest (`ci.run_id`), for the
  manifest and for both images;
* that run: trusted workflow file, `main`, same head commit, `completed` +
  `success`, and it uploaded the artifact `release-manifest-<sha>` (unexpired).

The rollout CLI performs this verification **before reading the target
configuration or contacting any host**; `verify-release` refuses to run
without a receipt for the exact manifest digest and stores the verified
manifest bytes + receipt under `<ops_root>/rollout/` as evidence; rollout state
is bound to the manifest digest (`state.bind_manifest`), so a replaced manifest
invalidates all earlier phase evidence.

Local rehearsals use a **separate fixture mechanism** (`fixture` subcommand,
`FixtureVerifier`, `LOCAL_FIXTURE_POLICY`): an unsigned envelope in the same
shape with a distinct issuer/repository/workflow identity. It is consulted only
under `--local` and can never satisfy the trusted policy (tested on every axis).

The CI trust chain (checkout, login, build/push, uv, manifest generation,
attestation, upload, download, proof) is pinned to full immutable commit SHAs;
a unit test enforces SHA pins repository-wide and checks the release-authority
job shape (trigger, permissions, ordering, attestation count).

## Trust boundary (explicit)

* Verification needs **network access to GitHub** (attestation API, Sigstore
  public-good trust root/transparency log, Actions API) and a **`gh` login**
  with read access to the repository and its packages. It is not
  offline-verifiable in the operator flow; when it cannot be performed the
  rollout fails closed for staging/production.
* **GitHub and repository administration are part of the trust boundary.** A
  compromise of the trusted workflow file, of `main` (branch protection,
  reviewers), of the repository's Actions/attestation settings, of the GitHub
  OIDC issuer, or of Sigstore is outside the protection this control provides.
  Structural validation prevents malformed manifests; image verification
  prevents incompatible/mismatched images; provenance verification establishes
  trusted release authority *within* that boundary.
* PR runs (same repository) attest a mechanically generated manifest with the
  `ci.yml` identity and the CI job proves the policy rejects it; fork PRs get no
  OIDC token and cannot produce provenance at all. PR manifests are never
  uploaded as artifacts.

## Consequences

* The deployable manifest is always the artifact of the Delivery run of the
  actual merged-main commit, never a PR head build.
* Operators need `gh` (authenticated) on the machine that runs the rollout.
* Renaming/moving `staging.yml`, changing the default branch, or changing the
  trusted repository requires a coordinated change of `TRUSTED_POLICY` (a
  security change reviewed like this ADR).
* The first real end-to-end attestation runs on the next push to `main`; until
  then the real `gh` path is exercised by CI (proof job + PR negative proof),
  and the policy logic by fixtures in the unit suite and the rehearsal.
