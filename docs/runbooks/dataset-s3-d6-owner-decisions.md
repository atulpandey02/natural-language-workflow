# Dataset S3 D6 owner decisions (OPEN — not chosen by engineering)

Status: **every decision below is open.** The
[D6 proof](dataset-s3-d6-proof.md) may not start until each row has the
owner's answer and the session is authorized in writing. Each item gives the
options and an engineering recommendation; the recommendation is not a
decision.

E11, E12 and E13 are **required before D6**: the procedure refuses to start
without E11 = `iam-user-mfa`, and P03-11 checks E12.

Answers that are identifiers or contact details (E4's recipient, E5, E8, E9,
E12) are given to the operator running
the proof and are **never committed** to this repository.

| Id | Decision | Options | Recommendation |
|---|---|---|---|
| **E1** | CloudTrail audit retention (`<AUDIT_RETENTION_DAYS>`) | (a) 90 days, the proof only; (b) 400 days, covering a year of access review plus a margin; (c) a period set by O-3/O-5 legal retention | **(a) for the proof**, with the bucket's default retention raised to the O-3/O-5 value before any customer object is stored. Retention can be lengthened later but, in COMPLIANCE mode, never shortened. |
| **E2** | Object Lock mode on the audit bucket | (a) GOVERNANCE: the audit administrator can shorten retention with `s3:BypassGovernanceRetention`; (b) COMPLIANCE: nobody, including the account root, can delete a log or shorten retention before it ends | **(a) GOVERNANCE for the proof.** COMPLIANCE makes every proof log, and the bucket itself, undeletable for E1's full period. Choose COMPLIANCE for the long-lived staging and production audit buckets, once E1 is final. |
| **E3** | Proof resources after the proof | (a) delete: X06 and X07 remove the dataset bucket, runtime roles, dataset key and trail; (b) retain: they become the staging dataset resources for O-6 | **(b) retain**, if the proof passes cleanly. It avoids re-provisioning and a second proof of identical templates, and the retained cost is small (E4). Choose (a) if the proof fails or the templates change. The proof instance and objects are always removed; the audit bucket, audit key and audit roles are always retained. |
| **E4** | Monthly cost ceiling and its alert | (a) USD 10 above the account's current monthly baseline; (b) USD 25 above it; (c) another figure; plus the alert recipient | **(b) the current baseline plus USD 25.** P03-00 creates an AWS Budgets alert at 80% of that figure and verifies it before any other resource. The budget is account-wide (a tag-filtered budget would need a cost-allocation tag activated first), so its limit must include the existing staging spend. A budget **alerts; it does not stop spending.** The proof's own increment is a few dollars a month (two KMS keys, a small trail, near-empty buckets) plus the proof day's instance hours and requests; confirm prices at provisioning time. |
| **E5** | Approved AWS account id | the account that holds staging today, or a separate staging-data account | **The account that already holds the staging host**, so the instance-profile design applies unchanged. A separate account would need cross-account trust, which ADR-033 does not cover. |
| **E6** | Final staging bucket naming | The proof always creates `nlw-staging-datasets-<ACCOUNT>-us-east-1-d6<12 random hex>`, so it can never adopt a bucket that already exists (P03-06). If E3 = retain: (a) keep that suffixed name as the staging bucket; (b) later create an unsuffixed bucket and re-run the proof on it | **(a) keep the suffixed name.** The application accepts it (`-[a-z0-9]{1,16}`), and it is the one the proof verified. (b) means provisioning and proving again. The staging audit bucket name is exactly 63 characters, the S3 maximum; the same pattern with `production` would be 66 and invalid, so the production names need a shorter form in the production provisioning review. |
| **E7** | An account-wide management-event trail already exists | (a) yes, multi-region, protected; (b) yes, but unprotected or single-region; (c) no | Confirm before P03 from P02's `p02-existing-trails.txt`. **If (b) or (c), stop:** bucket-policy, key-policy and IAM changes would go unrecorded. Creating that trail is a separate, account-level change. |
| **E8** | `<ADMIN_ROLE>`: the role that provisions and administers the dataset bucket and key | the owner's existing administration role, or a new, narrower provisioning role | **The existing administration role**, reached through the owner's MFA-protected sign-in. Record its exact ARN, including any path such as an IAM Identity Center prefix, because the bucket policy compares it exactly. Give it as the **role name with any path** (for example `aws-reserved/sso.amazonaws.com/AWSReservedSSO_Admin_0123456789abcdef`), never as an ARN: the templates build `arn:aws:iam::<ACCOUNT>:role/<ADMIN_ROLE>`, and `lib.sh` refuses an ARN (S1). The admin profile assumes it from the operator's IAM user with MFA, so its trust must allow that user. |
| **E9** | Human principals for the operator, audit-admin and audit-reader roles | named people or groups for each | **Two different people** for operator and audit administrator, so no one person can both purge data and alter its audit record. The audit reader may be either. Each must have an MFA device. |
| **E10** | Where the proof runs | (a) a disposable proof instance (P03-10) in the default VPC; (b) the staging host itself | **(a) the disposable instance.** It needs no change to the staging host, and the proof can be torn down without touching it. Steps P14 and P15 are repeated on the staging host when the refresher ships (O-6). If the account has no default VPC, the owner names a subnet instead. |
| **E11** | Human identity source for the operator, audit-admin and audit-reader roles | (a) IAM users with an MFA device, using long-term access keys on the workstation as the source profile; (b) IAM Identity Center (or another federated sign-in) | **Required before D6; not chosen here.** `trust-human-mfa` requires `aws:MultiFactorAuthPresent = true` and denies sessions where the key is absent. Identity Center sessions reach these roles by role chaining, where that key is generally absent, so with (b) the current template **fails closed** and no human can assume the roles. The procedure therefore supports only (a), whose cost is long-term access keys for humans on the workstation. Choosing (b) requires a separately reviewed trust-policy design (for example, trusting the Identity Center permission-set role with its own MFA enforcement) before D6. With (a), each person creates a **new access key only for this run**, enters it only at the macOS Keychain prompt in P00-03 (never in a file, variable, chat or ticket), and the proof deletes it in IAM (X09) and removes the Keychain items (X08). P00-03 verifies that each source identity really is an IAM user in its E9 list. Another workstation operating system needs a reviewed credential design first. |
| **E12** | Who may pass the bootstrap role (`iam:PassRole`) and launch or attach an instance with it (`ec2:RunInstances`, `ec2:AssociateIamInstanceProfile`, `ec2:ReplaceIamInstanceProfileAssociation`) | (a) only `<ADMIN_ROLE>`, enforced by a service control policy or permissions boundary outside this repository; (b) `<ADMIN_ROLE>` and named break-glass principals; (c) leave existing account administrators unrestricted | **(a) or (b).** Anyone who can launch an instance with the bootstrap profile obtains API and ingest credentials. The six dataset and audit roles deny these actions explicitly (`NeverPassOrAttachDatasetRoles`), and P03-11 simulates that. Other principals are outside these templates: list in `E12_MUST_NOT_PASS_JSON` the ones that must not, and P03-11 checks each. A restriction for every other administrator needs an account-level control that this repository does not create. |
| **E13** | Bucket-level list calls (`ListBucket`, `ListBucketVersions`) may be missing from the data-event trail | (a) accept: object-level events are recorded, and listings by the operator are rare and need MFA; (b) require them: a reviewed selector change and a re-proof | **Decide after P13 reports `p13-list-events.txt`.** If the count is non-zero, nothing is needed. If it is zero, (a) is reasonable for staging, but the gap must stay a documented residual risk until (b) is done for production. |

**Sign-off:** owner, date, and the authorized proof window.
